# v0.13.0 — 2026-08-05

Système Noeud + Composant (architecture à la Unity) : un Noeud générique
(transform, tag, calque) sur lequel s'attachent des composants indépendants,
en remplacement des données figées par type d'objet.

## Ajouté

- **Classe `Composant` + `Registre`** (`moteur/js/composant.js`) — base commune
  de tous les composants, registre indexé par type pour les Systèmes
  pseudo-ECS et le popup d'ajout.
- **Mixin `Noeud`** (`moteur/js/noeud.js`) — `getComponent`/`getComponents`/
  `addComponent`/`removeComponent` sur tout `THREE.Object3D` construit par le
  moteur.
- **9 composants** : `Mesh` (MeshFilter + MeshRenderer combinés, à la Unity —
  géométrie éditable avec option **Personnalisée** référençant un mesh importé,
  matériau toujours référencé en asset, jamais de champs bruts en repli),
  `Lumiere`, `Camera`, `Collider`, `Physique` (+ `SystemePhysique`), `Terrain`,
  `Particules` (+ `SystemeParticules`), `Reflexion`, `ScriptJS` (+
  `SystemeScripts`, bloc `@expose nom {type} = defaut` pour les variables
  exposées, API `api.noeud`/`api.trouverNoeud`/`api.trouverParTag`).
- **Ajouter un composant à n'importe quel Noeud** (y compris un objet « Vide »)
  via le bouton **+ Composant** de l'inspecteur (popup catégorisé, recherche).
  Chaque composant construit lui-même l'objet Three.js qui lui manque s'il est
  ajouté après coup (lumière, caméra, géométrie de terrain…) et retague
  `userData.type` pour rester reconnu par les systèmes existants (physique,
  particules, sondes).
- **Format de sauvegarde v8** (`moteur/js/serialisation.js:MIGRATIONS[7]`) —
  aucun changement de schéma sérialisé : les composants miroitent les bags
  `userData` déjà lus par le moteur existant. `synchroniserComposants()`
  (`migration-composants.js`) peuple `userData.components` à la reconstruction
  d'une scène, quelle que soit sa version d'origine.

## Modifié

- `appliquerMateriauSur()` (`materiaux.js`) et les filtres de corps rigide de
  `physique.js` reconnaissent désormais un Noeud porteur du composant `Mesh`,
  pas seulement `userData.type === 'mesh'`.
- La boucle de frame (`viewport.js`) appelle `SystemePhysique.update()` /
  `SystemeScripts.update()` / `SystemeParticules.update()` au lieu d'appels
  directs épars ; ordre inchangé (scripts avant physique, comme avant).

## Corrigé

- Retirer le composant `Mesh` d'un objet ne faisait rien visuellement — la
  géométrie Three.js restait affichée. `Mesh.onRetrait()` vide maintenant
  vraiment `mesh.geometry`.
- `this.material` était mis en cache à la construction du composant `Mesh` ;
  après un changement d'asset matériau (qui remplace l'objet `material` par
  une nouvelle instance), le composant pointait sur l'ancien. C'est maintenant
  un getter qui lit toujours `this.noeud.material`.

## Notes

**Portée non couverte** : `runtime-jeu.js` (le runtime du build exporté)
duplique certains filtres par `userData.type` (caméras, sondes, corps rigides)
qui n'ont pas été mis à jour pour reconnaître les composants ajoutés à un
objet Vide — seul l'éditeur est concerné par ce lot. Un projet exporté en
build avec un objet Vide + composants devra être revérifié séparément.

Les 11 fichiers de test pilotant un navigateur (Playwright) ont été supprimés
de `moteur/test/` à la demande explicite de l'utilisateur, avec la dépendance
`playwright` retirée de `moteur/package.json` — le test manuel dans le
navigateur remplace cette couverture pour ce lot.
