# v0.185.0 — un plugin peut faire entrer un fichier dans le projet

Ajoute `Editor.api.importFiles(files, opts)` à l'API des plugins, et livre
`exemples/plugin-evaveo-studio.js` — le patron pour brancher n'importe quel outil externe sur
l'éditeur.

## Le mètre qui manquait

Un plugin qui va chercher un modèle ailleurs — un studio d'asset local, une bibliothèque en
ligne — pouvait le télécharger et **ne rien en faire**. `importFiles` existait dans
`js/assets.js` mais n'était ni exportée en globale ni présente dans `Editor.api` : le plugin
devait demander à la personne de glisser le fichier elle-même.

Ce n'était pas une protection. Un plugin s'exécute **déjà** avec tous les droits de la page —
c'est écrit en tête de `docs/PLUGINS.md`. Ne pas exposer la fonction n'ajoutait aucune barrière,
seulement un mètre manquant au bout d'un chemin qui marchait.

L'entrée **délègue** au chemin ordinaire du glisser-déposer. L'asset obtenu est donc
indiscernable d'un asset glissé : pas de second chemin d'import à maintenir, et tout ce que
l'éditeur sait faire d'un `.glb` — matériaux, animations, prefabs — marche sans une ligne de
plus. Le test vérifie la **délégation**, pas la présence d'un nom.

## Le patron : brancher un outil externe

`exemples/plugin-evaveo-studio.js` relie l'éditeur à **EVAVEO 3D Studio**, une application Python
séparée qui pilote Blender et exporte des GLB. Le plugin ajoute un panneau : liaison, export,
liste des fichiers produits, import en un clic.

```
outil → son API HTTP locale → plugin → Editor.api.importFiles([...]) → asset du projet
```

### Trois bornes, parce qu'un tel plugin devient une porte s'il ne s'en met pas

1. **L'adresse doit être locale.** `127.0.0.1`, `localhost` ou `[::1]`, vérifiée en **analysant
   l'URL** et non par une sous-chaîne : `http://127.0.0.1.exemple.com/` contient « 127.0.0.1 » et
   n'est pas locale. Le refus est **à la saisie**, pas seulement à l'appel — laisser entrer une
   adresse distante puis la refuser plus tard donnerait l'impression qu'elle est acceptée.
2. **Les octets doivent être un GLB.** Signature `glTF` vérifiée avant l'import. Un service qui
   répondrait une page d'erreur HTML donnerait sinon un asset vide et une panne qu'on chercherait
   dans le moteur. Plafond à 256 Mo.
3. **Les chemins viennent du service, jamais de la saisie.** Le plugin n'en construit aucun.

Le jeton de session est masqué à l'affichage (`••••••••hKgw`) et retaper la valeur masquée
n'écrase pas le vrai jeton.

### Côté service : l'ouverture est explicite, et ce n'est pas au moteur de la décider

Le Studio **refuse** par défaut les appels venus d'une autre page — c'est ce qui le protège d'un
site ouvert dans un autre onglet, et c'est le bon défaut. Il se lance donc avec
`--allow-origin http://127.0.0.1:8080` pour parler à l'éditeur (correctif fourni avec le Studio,
hors de ce dépôt).

Quand l'option manque, le navigateur masque le refus derrière un échec réseau opaque. Le plugin
traduit : *« Le Studio ne répond pas à …, ou il refuse cette page. Relancez-le avec :
python studio.py --allow-origin http://127.0.0.1:8080 »* — avec l'origine réelle de la page.

Jamais `Access-Control-Allow-Origin: *` : avec un jeton en en-tête, `*` laisserait n'importe
quelle page tenter sa chance.

## Aussi

Deux tests étaient **rouges sur toute machine Windows** et verts en CI : leurs expressions
régulières cherchaient `\n` dans un fichier source, et ce dépôt se checkout en **CRLF**
(`core.autocrlf`). `test/donnees-trompeuses.test.mjs` tombait même sur un `TypeError` qui ne
désignait rien — on aurait cherché la panne dans le copilote. Les deux acceptent maintenant
`\r?\n`. C'est la pire forme de rouge : celle qu'on apprend à ignorer, et qui masque les vraies
régressions.

`docs/PLUGINS.md` gagne `importFiles` dans le tableau de l'API et une section **9. Brancher un
outil externe** qui écrit les trois bornes et la règle d'ouverture explicite.

## Vérifié dans le vrai éditeur

Plugin installé et exécuté dans la page : chargement sans erreur, panneau enregistré avec ses
deux sections (id préfixé `u-…:evaveo-studio`), et **liaison établie à travers les origines** —
« Connecté — 0 fichier(s) exporté(s) » avec le Studio lancé sur `--allow-origin`. Les trois
bornes ont été éprouvées depuis la page : adresse distante refusée, sous-domaine piège refusé,
`localhost` accepté, jeton masqué non écrasable. Et sans l'option côté Studio, le message
d'erreur donne la commande exacte.
