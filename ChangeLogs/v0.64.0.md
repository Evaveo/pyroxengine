# v0.64.0 — 2026-08-17

**Le copilote peut voir, essayer et mesurer.** Il savait agir — 31 commandes qui créent, transforment,
peignent — et rien d'autre. Il construisait donc des scènes qui « réussissent toutes les commandes et
produisent un niveau injouable » : la description de `analyser_scene` le disait déjà, et un contrôle
statique n'y suffisait pas.

Le raisonnement derrière ce lot : **tous** les défauts réels de cette session ont été trouvés en
regardant une image ou en lisant une mesure. Le personnage flou (rapport pixel 0,694), la plateforme
inatteignable (elle existait, hors champ), le demi-écran vide, les mailles empilées par centaines.
Aucun n'était visible depuis le texte d'une commande.

## Les trois commandes

| Commande | Rend | Sans elle |
|---|---|---|
| `capturer_vue` | une image de la vue d'édition | un cadrage ou un objet hors champ est invisible |
| `jouer_et_mesurer` | le jeu **lancé pour de vrai**, positions au fil du temps + image | rien ne dit si le jeu fonctionne |
| `verifier` | rapport pixel, boîtes de collision, problèmes de chaque carte | les nombres qui décident étaient internes |

`jouer_et_mesurer` lance **`apercu-jeu.html` dans un cadre invisible** — le même code qu'un build
publié, pas une simulation approchée : ce qu'on mesure est ce que le joueur aura.

## Le résultat, sur le cas qui compte

Un sol percé d'un trou, un héros lâché au-dessus :

```
t=0.761s : Héros(7.5, -11.3904, en l'air)
t=1.594s : Héros(7.5, -36.0912, en l'air)
t=2.427s : Héros(7.5, -69.7639, en l'air)
t=3.261s : Héros(7.5, -103.4472, en l'air)
```

Il tombe dans le vide, et **ça se lit d'un coup d'œil**. L'échantillonnage n'est pas décoratif : un
héros tombé dans un trou et un héros posé au sol peuvent finir au même endroit — seule la trajectoire
les distingue.

Sur un sol intact, la même commande rend `Héros(4, -7.55, au sol)` et `Caméra 2D(4, -6.8)` : la
surface du sol (−8) plus la demi-hauteur du collider (0,45), et la caméra à `−7,55 + 6,28 × 0,12`.
Les chiffres exacts que je mesurais à la main toute la session.

## ⛔ Une correction : j'avais annoncé un suivi de caméra qui ne tournait pas

En v0.59.0 j'ai écrit « la caméra 2D suit sa cible en mode jeu dans l'éditeur ». **C'était faux.**
`modeJeu.actif` **ne devient jamais vrai** — le bouton ▶ ouvre `apercu-jeu.html` dans un onglet, et
`js/mode-jeu.js` le dit noir sur blanc : « ces branches restent inertes ». Mon
`if(modeJeu.actif && …) majCamera2d(objets)` était injoignable.

Je l'avais « vérifié » en appelant `majCamera2d` **à la main depuis la console**. Ça prouvait la
fonction, pas le câblage — exactement le piège d'avoir raison pour une mauvaise raison. L'appel mort
est retiré, et le suivi est désormais **prouvé là où il tourne** : dans le runtime, par
`jouer_et_mesurer`.

À signaler, hors périmètre : il reste **28 branches** sur `modeJeu.actif` dans le dépôt, dont 13 dans
`viewport.js` — parmi lesquelles l'appel à `pasMonde2d`, ce qui veut dire que la physique 2D ne tourne
pas non plus dans l'éditeur. Ce n'est pas un défaut de cette version, mais ça mérite un ménage.

## Le contrat des commandes, élargi

L'ancien contrat était `String(exec(args))` — synchrone, et du texte. Il interdisait précisément les
trois choses ci-dessus. Désormais une commande peut rendre une chaîne (comme avant), une promesse, ou
`{texte, image}`. **Les 31 commandes existantes n'ont pas bougé d'une ligne.**

Deux détails qui décident du résultat :

- **Une image part en bloc `image`, jamais en base64 dans le texte.** Dans le texte, le modèle ne la
  voit pas : il lit quarante mille caractères de bruit qui noient son contexte. Vrai des deux côtés —
  l'API et MCP, qui a son propre type `{type:'image', data, mimeType}`.
- **La boucle d'agent est passée de `forEach` à `for…of`.** Un `await` dans un callback de `forEach`
  n'est pas attendu : les résultats seraient partis vides et le modèle aurait enchaîné sur un état
  qu'il ne connaît pas.

## Le runtime expose une lecture seule

`runtime-jeu.js` est enveloppé dans une IIFE : rien n'y est joignable de l'extérieur. C'est voulu, et
ça coûtait cher — pour savoir où tombait le héros, il fallait glisser un script **dans la scène**.
`window.__etatJeu()` rend maintenant le temps et, par objet, nom, position, contact au sol et vitesse
verticale. **Aucun setter** : observer n'est pas piloter, et un test le vérifie.

## Deux garde-fous nés d'erreurs de ce lot

- **`test/syntaxe-js.test.mjs`** : une parenthèse manquante dans le fichier neuf est passée jusqu'au
  navigateur, et le symptôme n'était pas « erreur de syntaxe » mais « outil inconnu :
  capturer_vue ». Un `<script>` qui ne parse pas est **ignoré en silence** : la page marche, il manque
  seulement tout ce que ce fichier déclarait. `lint-ordre-chargement.mjs` vérifiait l'ordre, jamais le
  contenu. La garde utilise `node --check` — une première version découpait les `import` à la regex et
  accusait `protocole-mcp.mjs` d'une faute qu'il n'avait pas.
- **La capture vide est refusée**, pas rendue. Un canvas WebGPU peut rendre une image entièrement
  transparente sans lever d'erreur, et l'agent la lirait comme « la scène est vide » — puis se mettrait
  à réparer ce qui n'est pas cassé. Le message le dit explicitement.

`verifier` a d'ailleurs trouvé son propre défaut à la première exécution : il répondait
`genre: "3d"` juste après un préréglage 2D, parce que `projet.scenes[…].donnees` n'est rafraîchi que
par `construireDonneesProjet`. Il lisait l'état d'avant. Corrigé.
