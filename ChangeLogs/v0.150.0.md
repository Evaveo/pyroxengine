## Ajouté

### Confirmation avant d'exécuter le code d'un projet qu'on n'a pas écrit

Un script de projet **voyage dans le fichier** : ouvrir le projet de quelqu'un d'autre, c'était
exécuter son code, sans question. Le gain le plus direct pour un attaquant n'était pas d'abîmer
la scène — c'était de lire la clé d'API du copilote et de l'envoyer ailleurs. Deux lignes.

L'éditeur demande désormais confirmation, **une fois**, en nommant les scripts concernés. Refuser
n'empêche rien d'autre : le reste de l'éditeur fonctionne normalement, et les scripts restent
lisibles dans le panneau Projet avant de décider.

**La confiance suit la paternité**, et c'est ce qui rend la garde vivable :

- un script que vous écrivez ou modifiez dans l'éditeur est accepté **au moment où vous
  l'enregistrez** — jamais de question sur votre propre travail ;
- le projet d'un tiers pose la question une fois, et la réponse vaut pour la suite ;
- **une mise à jour de ce projet la repose** : le code a changé, donc il n'a toujours pas été
  écrit par vous. C'est le cas le plus vicieux, et une confiance par projet l'aurait raté.

La clé est l'empreinte du code, pas le nom du projet — deux projets nommés « Test » ne partagent
pas leur confiance. Les fins de ligne sont normalisées avant l'empreinte, sinon un aller-retour
Windows/LF reposerait la question sans raison compréhensible, et on apprendrait à répondre oui
sans lire.

**Deux portes, parce qu'une seule laisserait croire le vecteur fermé** : la compilation dans
l'éditeur (simulation physique, lecture d'animation) et le bouton ▶ Jouer — qui ouvre un onglet
de **même origine**, donc avec le même accès au stockage que l'éditeur.

**Le jeu publié n'a pas cette porte, et c'est une décision** : un joueur qui télécharge un jeu a
déjà choisi de le lancer.

### ~~Portée réduite pour les scripts de projet (v0.149.4)~~ — **RETIRÉ en v0.150.1**

> Ce durcissement a cassé l'interface HTML de tout jeu qui en a une : les scripts de projet
> pilotent le DOM (fonctionnalité UIDocument), et `document` était masqué. Il est retiré.
>
> Il était de surcroît **illusoire** : tant que `window` doit rester accessible — et il le
> doit —, `window.fetch` et `window.localStorage` le sont aussi. La protection réelle est la
> confirmation ci-dessus, qui ne suppose rien de ce dont un script a besoin.
>
> Détail de la cause et de la mesure fautive : [`docs/KNOWN_ISSUES.md`](../docs/KNOWN_ISSUES.md).
> Le paragraphe d'origine est conservé ci-dessous.



`fetch`, `localStorage`, `document`, `globalThis` et une vingtaine d'autres globales ne sont plus
visibles depuis un script de projet : elles deviennent des paramètres laissés vides. `Function`
en fait partie — `Function('return this')()` était le contournement classique.

**Ce n'est pas un bac à sable**, et le code le dit : `eval` n'est pas masquable en mode strict.
C'est une réduction de surface ; la vraie parade est la confirmation ci-dessus. Une garde qu'on
croit étanche est pire qu'une garde absente.

Les plugins ne sont pas touchés, **après mesure** : ils ne voyagent pas dans un projet (ils
vivent dans le stockage du navigateur, collés délibérément). Les durcir n'aurait rien protégé et
aurait cassé la seule API d'extension de l'éditeur.

## Corrigé

### Des réglages disparaissaient à la publication (v0.149.2 et v0.149.3)

Trois réglages tenaient dans l'éditeur, survivaient à la sauvegarde et au rechargement — puis
disparaissaient dans le jeu publié, sans erreur ni message :

- **les ombres par objet** : un objet décoché « projette une ombre » en projetait quand même une ;
- **le LOD** : le système était bien embarqué et tournait à chaque image… sur zéro objet ;
- **la lightmap d'atlas** : les objets partageant un atlas cuit recevaient l'éclairage d'un autre
  objet. La cause n'était pas une ligne oubliée mais une **dépendance** — la fonction de
  replacage vivait dans un fichier impossible à embarquer. Elle a désormais son module partagé
  (`js/lightmap-atlas.js`).

### Du code injoignable dans le runtime (v0.149.1)

Une branche recopiée **sans son consommateur**, avec un nom de hook fautif que personne ne
pouvait voir échouer — du code injoignable ne casse jamais. Retirée.

## Gardes ajoutées

Un correctif sans garde se défait au merge suivant, et ce dépôt en a l'expérience. Chaque
correction ci-dessus en a une :

| Garde | Ce qu'elle refuse |
|---|---|
| `test/script-confiance.test.mjs` | qu'une version modifiée hérite de la confiance de la précédente ; qu'une des deux portes disparaisse ; que le module parte dans un build |
| `test/script-portee.test.mjs` | qu'un des trois sites recompile un script dans la portée globale ; qu'un nom rende tout script incompilable |
| `test/project-roundtrip.test.mjs` | qu'un champ de nœud écrit dans le fichier ne soit pas relu **par les deux moteurs**, sauf exception avec sa raison écrite |
| `test/surface-three-webgpu.test.mjs` | qu'un hook three soit écrit à une lettre près |
| `test/lissage-tsl.test.mjs` | le retour de la branche GLSL injoignable |

Deux d'entre elles ont commencé par attraper une erreur de leur propre auteur : une exception
déclarée à tort, et un mot anglais glissé dans un texte français de l'interface — le même piège
que le « linéarea » de l'aide.
