# v0.98.0 — paramètres du projet, préférences, API de plugin v2

Lot 3 de la refonte de l'interface. Trois chantiers : le format dossier réparé, les réglages
rangés là où ils appartiennent, et l'API de plugin passée au socle déclaratif.

## Cassant

**`Editor.version` passe de `'1.1'` à `'2.0'`.** Trois retraits d'API publique de plugin :

- **`Editor.registerInspector({forType, html, sync, input, click})` est supprimée**, remplacée
  par `Editor.registerInspectorSection({forType, id, title, sections})`.
- **`registerTypeObject({inspector: {html, sync, input, click}})` n'accepte plus que
  `{inspector: {sections}}`** — le même contrat, oublié par tout le monde parce qu'il ne portait
  pas le même nom.
- **`Editor.api.fields` (number, text, color, select, vec3) est retirée.** Ces cinq fabriques
  rendaient des chaînes HTML, que l'auteur du plugin devait ensuite retrouver par
  `getElementById` et router lui-même. C'est exactement l'interface que la refonte vient de
  retirer de l'éditeur : la laisser aux plugins l'aurait gardée vivante.

**Migration, en dix lignes.** Avant :

```js
inspector: {
  html:  function(o){ return '<div class="sec">Borne</div>'
                           + Editor.api.fields.number('bportee', 'Portée', 0.5, 1, 50); },
  sync:  function(o){ const el = document.getElementById('f-bportee');
                      if(el && document.activeElement !== el) el.value = o.userData.borne.range; },
  input: function(o, id){ if(id !== 'f-bportee') return;
                          o.userData.borne.range = parseFloat(document.getElementById(id).value) || 5; }
}
```

Après :

```js
inspector: { sections: [{ id: 'borne', title: 'Borne', fields: [
  { label: 'Portée', type: 'number', step: 0.5, min: 1, max: 50,
    get: (o) => o.userData.borne.range,
    set: (o, v) => { o.userData.borne.range = v || 5; } }
]}]}
```

Le socle construit, synchronise, borne la saisie et route les événements. Le plugin d'exemple du
dépôt (Fichier → Plugins → « Voir un exemple ») est réécrit au contrat v2.

**Ce qui n'est PAS cassé.** `def.type` d'un type d'objet et `typeName` d'un composant ne sont
**pas** préfixés par l'identifiant d'installation : ils finissent dans `userData.type` et dans
le projet **sérialisé**, et les préfixer rendrait illisible tout projet déjà enregistré. Le
préfixe ne protège que l'interface — ids de panneau, de section d'inspecteur, de type de champ,
clés de préférence.

**Pourquoi un MINOR et pas un MAJOR.** `ChangeLogs/VERSIONING.md` classe la suppression d'une
API publique en MAJOR, avec une clause explicite « avant 1.0.0 » qui autorise le cassant en
MINOR **à condition de l'expliquer**. C'est ce que fait cette section. Le raisonnement, en
clair : l'éditeur n'a pas encore de version 1.0, l'API de plugin n'a pas d'implémentation
tierce connue hors du dépôt, et geler pour une version majeure un contrat qui construit du HTML
à la main aurait obligé chaque plugin futur à naître périmé.

**Trou connu, non résolu.** `registerCommandMenu` et `registerMaterial` ne sont indexés par
aucun identifiant — ils se repèrent par `menu.title` et `def.name` — et restent donc non
protégés contre la collision entre deux plugins. C'est un choix de portée, pas un oubli : les
protéger demande de leur donner un id, donc de casser une seconde fois.

## Ajouté

- **`project.settings`** : les huit réglages de niveau projet (nom, calques, calques 2D, pixels
  par unité, entrées, cuisson, document de conception, affichage de la version) plus
  l'environnement de départ d'une nouvelle scène. `project.layers` &co. restent des
  **accesseurs** dessus — une façade, pas un second exemplaire de la donnée.
- **`Prefs`** : un registre de préférences d'éditeur, avec libellé, type, catégorie et valeur
  par défaut déclarés. Une seule clé `localStorage` en écriture. Les clés nues existantes sont
  **importées sans être supprimées** (voir « Corrigé »), et un écouteur `storage` recharge les
  préférences quand un autre onglet écrit.
- **Deux fenêtres dockables** : « Paramètres du projet » (menu Fichier) et « Préférences »
  (menu Édition). Des panneaux et non des modales : une fenêtre de réglages qu'on ne peut pas
  laisser ouverte à côté de la vue force un aller-retour par essai. Les trois modales qu'elles
  remplacent (`modalLayers`, `modalInputs`, la convention de nommage) y renvoient.
- **API de plugin v2** : `registerPanel` (un panneau du dock, comme ceux de l'éditeur),
  `registerFieldType` (un type de champ du socle), `definePref` (une préférence, qui apparaît
  seule dans la fenêtre Préférences), `defineProjectSetting` (un réglage qui voyage avec le
  projet), `registerInspectorSection`.
- **Migration du format dossier** : `migrateManifestFolder` et `migrateSceneFile`, avec une
  version **par fichier de scène**.

## Corrigé

- **Le format dossier ne migrait pas du tout.** `migrateProjectData` n'avait qu'un appelant, sur
  le chemin `.p3d` ; `loadProjectFromFolder` ne lisait même pas `manifest.version`. Tout palier
  ajouté s'appliquait aux `.p3d` et sautait les dossiers — deux formats du même projet qui
  divergent en silence. La migration est **par fichier de scène** et non au manifeste, parce que
  l'enregistrement n'écrit que la scène courante : un numéro unique aurait menti sur les autres.
- **Le manifeste d'un dossier perdait sept champs de projet à chaque enregistrement** — entrées,
  calques, calques 2D, pixels par unité, cuisson, document de conception, affichage de la
  version. Ils étaient dans les données du projet depuis toujours, et le manifeste ne les
  écrivait pas.
- **La modale des plugins ne s'ouvrait plus dès qu'un plugin était installé.** Les collections
  y étaient citées sous leurs anciens noms français (`typesObjets`, `materiaux`), qui ne sont
  plus des propriétés d'`Editor` : `undefined.filter` levait. Retirer un plugin ne purgeait donc
  ni ses types d'objets ni ses matériaux.
- Un plugin chargé avant la barre de menus se coupait en deux sur un `ReferenceError` :
  les écritures dans la coquille (entrée de menu, type créable) sont maintenant **différées** et
  réalisées par `bootPluginsUi()`.

## Ce qui n'a PAS été supprimé, et pourquoi

Les clés `localStorage` nues (`copilot-key`, `moteur3d-plugins`, `moteur3d-nommage`,
`moteur3d-layout`) sont **importées et continuent d'être écrites**. Trois raisons mesurées : la
clé API du copilote est lue directement à six endroits ; deux onglets de l'éditeur partagent le
même stockage sans se parler ; et l'éditeur tourne en local, sans déploiement atomique — une
version antérieure rouverte ensuite ne trouverait plus rien. La suppression sera annoncée dans
un ChangeLog ultérieur.

`jeu3d:*` (les sauvegardes des joueurs) et `window:*` (la géométrie des fenêtres flottantes) ne
sont **pas** des préférences et n'entrent pas dans le registre.

## Format de projet

Version **15**. Un projet antérieur migre à l'ouverture, dans les deux formats. Le manifeste d'un
dossier passe à la version **2**, chaque fichier de scène à la version **1**.
