# v0.158.1 — un document d'interface est du code, et la garde l'ignorait

## Corrigé

### Le HTML d'un projet contournait la question de confiance

`js/script-trust.js` est la parade contre le code d'autrui : consentement par empreinte,
demandé une fois, redemandé si le code change. Elle ne regardait qu'un seul genre d'asset :

```js
return a && a.kind === 'script' && …
```

Or un asset `documentUI` porte du **HTML de projet**, que `js/game-ui.js` écrit dans
`innerHTML` sans filtre — c'est sa fonction, une interface de jeu est du HTML.

**La chaîne complète.** Un projet sans aucun script mais avec un document d'interface :
`untrustedCode()` ne trouvait rien → `allowRunScripts()` rendait `true` sans poser de question
→ entrée en mode lecture → `innerHTML`. Les balises `<script>` d'un `innerHTML` ne s'exécutent
pas ; **les gestionnaires en ligne, si** (`onerror`, `onload`). Ils tournaient dans la page de
l'éditeur, donc avec `localStorage` — où vit la clé du copilote — et avec `fetch`.

C'est la combinaison §1.2 + §1.3 de `docs/REVUE_2026-09-22.md`, par un chemin que la revue ne
nommait pas. Et l'échéance qu'elle annonçait — « bloquant dès l'ouverture d'un projet tiers via
`cloud/` » — est arrivée avec les v0.154 à v0.158 : projets hébergés, contributeurs multiples,
ouverture par URL.

**Rien ne le signalait.** La garde répondait « rien à demander » et avait l'air de fonctionner.

### Ce que le correctif fait, et ne fait pas

`codeOfAsset(a)` rend le code exécutable d'un asset quel que soit le champ qui le porte :
`code` pour un script, `html` pour un document d'interface. `scriptsUntrusted` devient
`untrustedCode` — le nom disait ce que la fonction ne fait plus.

**On ne cherche pas à distinguer le HTML « inerte » de l'exécutable.** Il faudrait un analyseur,
et un analyseur qui se trompe une seule fois rouvre le trou en entier : `onerror`,
`javascript:`, `srcdoc`, une `url()` dans un `style`. La règle retenue ne peut pas se tromper :
le HTML d'un projet est du code.

**Les feuilles de style n'y sont pas**, et c'est un choix mesuré : leur contenu part dans le
`textContent` d'une balise `<style>`, qui n'exécute aucun script. Il reste un canal
d'exfiltration faible, sans accès au `localStorage` ni au DOM. Un test existe pour rendre ce
choix visible, et dit où revenir si le CSS gagne un jour un chemin d'exécution.

La question posée nomme désormais la **nature** de chaque élément — « Menu — document
d'interface » situe la décision, « Menu » ne renseigne personne.

### La paternité vaut aussi pour le HTML

`js/assets.js` appelle `trustCode(a.html)` à l'enregistrement d'un document d'interface, comme
`js/scripts.js` le fait pour un script. Sans ça, la personne se verrait demander l'autorisation
d'exécuter ce qu'elle vient de taper — et une garde qui interroge sur son propre travail est
une garde qu'on désactive dans la semaine.

Cette ligne a été **trouvée manquante par un test de mutation** : la retirer ne faisait tomber
aucun test. Le test qui la garde a été ajouté.

### Un commentaire qui annonçait une protection disparue

`js/scripts.js` affirmait « PORTÉE RÉDUITE : `fetch`, `localStorage`, `document`… sont
masqués ». `GLOBALS_HIDDEN` est **vide** depuis la v0.150.1, et `js/script-scope.js` explique
pourquoi. Dans un fichier de sécurité, un commentaire qui décrit une garde absente est pire
qu'un commentaire manquant : le prochain lecteur croit le vecteur fermé.

## Tests

Quatre cas ajoutés à `test/script-confiance.test.mjs` : un document d'interface passe par la
question, celui qu'on vient d'écrire n'y passe pas, celui qui a changé y repasse, une feuille de
style n'y passe pas. Deux mutations vérifiées — l'ancien périmètre et la paternité retirée.
