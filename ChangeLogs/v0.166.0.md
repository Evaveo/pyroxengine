# v0.166.0 — cloud ou local, et un copilote qui coûte moins cher

## Added
- **Mode de stockage explicite** : badge « ☁ Cloud / 📁 Dossier / ⚠ Non enregistré » dans la
  barre du haut. Sonde `/api/moi` au démarrage (`cloud-session.js`) ; sans backend, l'éditeur
  reste en local sans rien signaler.
- **Fichier → Envoyer sur le cloud…** : crée le projet hébergé, envoie les fichiers (ceux que
  le serveur a déjà sont sautés), bascule en mode cloud (`?projet=N`).
- **Fichier → Télécharger en local…** : copie détachée (dossier ou .p3d) d'un projet cloud.
- **Fichier → Enregistrer dans un dossier…** : possible même sans avoir ouvert de dossier.
- Ctrl+S sur un projet jamais enregistré propose Cloud / Dossier / .p3d au lieu d'un cul-de-sac.
- Hub : « Créer directement sur le cloud » quand on est connecté.
- Copilote — inspection : `get_object`, `find_objects`, `get_hierarchy`, `read_script`,
  `read_console` (plus besoin de script sonde).
- Copilote — construction en lot : `batch`, `build_room`.
- Copilote — `load_tools` : un noyau de 20 outils, le reste par domaine à la demande.
- Coût affiché par message et par session.
- **Pont MCP** (`moteur/outils/mcp-bridge/`) : une IA locale (Claude Desktop/Code, LM Studio…)
  pilote l'éditeur ouvert dans le navigateur, via `mcp-link.js` (jeton, consentement par session).

## Changed
- Modèle par défaut du copilote : Sonnet (Opus reste au choix).
- Cache de prompt Anthropic (outils, système, dernier message) et compaction de l'historique
  au-delà de ~40k tokens.
- La première copie vers le cloud ou un dossier inclut les assets binaires.

## Fixed
- `configure_material` ignorait le lissage (le schéma disait `smoothing`, le code `smoothness`).

## Aussi publié en v0.166.0 sur la branche staging — l'export bureau (Electron)

Les deux branches ont numéroté leur version 0.166.0 en parallèle ; elles sont réunies en v0.173.0.

Troisième et dernier des manques rédhibitoires pour un studio : `exportBuildWeb` était la seule
cible. Un studio qui vend son jeu a besoin d'un exécutable.

### Ce que l'éditeur peut, et ce qu'il ne prétend pas faire

Il tourne dans un onglet. Il ne peut donc **pas** produire un `.exe` : compiler demande de lancer
des processus et d'écrire sur le disque, et un navigateur ne fait ni l'un ni l'autre. Le
prétendre serait la pire version de cette fonctionnalité.

Ce qu'il produit est un **projet Electron complet et correct** : le jeu, l'enveloppe, et les deux
commandes qui en font un exécutable.

```
npm install
npm run dist
```

`.exe` sous Windows, `.dmg` sous macOS, `.AppImage` sous Linux — compilés sur la machine cible.
Le message de fin de l'export rappelle les deux commandes, et le `LISEZMOI.md` du ZIP dit le
reste.

### Electron plutôt que Tauri, et pourquoi

Tauri donne des binaires dix fois plus petits, en s'appuyant sur la WebView du système —
WebView2 sur Windows, WKWebView sur macOS. Ce moteur rend en **WebGPU**, et sa prise en charge
dans ces WebView est inégale d'une version de système à l'autre. Un jeu qui rendrait correctement
chez l'auteur et pas chez le joueur est exactement la famille de défauts que ce dépôt passe son
temps à fermer.

Electron embarque son Chromium : le jeu exporté rend **ce que l'auteur a vu**. Le prix est d'une
centaine de mégaoctets par build, ce qui est la norme pour un jeu de bureau.

### Le piège qui tue tout si on l'ignore

`win.loadFile('index.html')` charge la page en `file://`, et **Chromium refuse les modules ES en
`file://`** — règle d'origine, pas un réglage. Or ce moteur est entièrement fait de
`<script type="module">`. Un Electron naïf donne donc une fenêtre noire, avec dans la console une
erreur de CORS que rien ne relie à l'emballage.

D'où le protocole maison `jeu://` enregistré dans `main.js`. Il est déclaré **standard** et
**sûr** : `standard` lui donne une origine véritable, ce qui débloque les modules ES **et** le
stockage local — c'est-à-dire les sauvegardes du jeu, sans une ligne de plus.

Le chemin demandé est vérifié : `jeu://app/../../secret` est refusé. C'est une application
locale, mais elle chargera un jour du contenu que l'auteur n'a pas écrit — un classement, une
publicité — et cette ligne ne coûte rien aujourd'hui.

### L'enveloppe reste étanche

`contextIsolation` actif, `nodeIntegration` éteint, `sandbox` actif. Un jeu exécute des scripts de
projet, et ce moteur laisse déjà ouvrir le projet d'autrui (`js/script-trust.js`) : exposer Node à
la page reviendrait à donner le disque entier au premier script venu.

Le pont expose **deux** fonctions — quitter, et le plein écran. Les deux seules choses qu'une page
web ne sait pas faire et qu'un jeu de bureau doit savoir faire.

```js
api.desktop()     // vrai dans l'application, faux dans un navigateur
api.quitGame()    // false sur le web, où c'est impossible
```

`api.quitGame()` rend `false` plutôt que de ne rien faire : un bouton « Quitter » doit se
**cacher** quand `api.desktop()` est faux, pas rester inerte sous le doigt.

### Une seule collecte pour les deux sorties

Web et bureau publient **exactement le même jeu** : même `index.html`, mêmes modules, même
allègement. `collectBuildFiles()` est extraite de `exportBuildWeb`, et les deux exports en
partent. Deux collectes séparées auraient fini par publier deux jeux différents, et l'écart ne se
serait vu qu'en comparant deux téléchargements.

### Ce que le LISEZMOI dit, et pourquoi il le dit

- **Épinglez les versions.** Le `package.json` demande des plages (`>=30.0.0`) pour que
  `npm install` réussisse aujourd'hui comme dans six mois. Un numéro que je ne peux pas vérifier
  rendrait l'installation impossible le jour où il n'existe pas. Un studio doit figer après la
  première installation, sinon deux compilations à deux dates ne rendent pas le même binaire.
- **Signez.** Sans signature, Windows affiche un avertissement SmartScreen et macOS **refuse**
  d'ouvrir le jeu. C'est un certificat payant, et ça se prévoit avant la date de sortie.
- **Ne remplacez pas le protocole** par `loadFile`, et pourquoi.

### Les gardes

`moteur/test/build-bureau.test.mjs` — quatorze tests. Le plus important : `main.js` et
`preload.js` sont **parsés pour de vrai** (`new vm.Script`), pas cherchés à coups d'expressions
régulières. Une apostrophe mal échappée dans un gabarit fait un fichier mort, et Electron l'ignore
en silence.

Le reste couvre les quatre pannes qui ne se découvrent qu'après `npm run dist` et une fenêtre
noire : le protocole, le dossier du jeu servi à côté de celui que le ZIP remplit, la divergence
avec la sortie web, et l'enveloppe percée.

**Dix mutations passées, dix attrapées** — la dixième après avoir resserré une assertion qui
cherchait le mot « signature » et le retrouvait dans sa propre prose après qu'on eut retiré la
section. On exige désormais la **conséquence** (« SmartScreen », « macOS refuse »), pas le mot.

Vérifié dans le vrai éditeur : le ZIP produit fait 797 Ko et 70 fichiers, l'enveloppe est
complète, le jeu est bien dans `jeu/` avec son `index.html` et son `data.js`, le `package.json`
se relit et porte `com.evaveo.mon-jeu-genial`, et `main.js` charge bien par `jeu://`.
